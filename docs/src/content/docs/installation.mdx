## The library

The `GitSnapshotter` package targets `net8.0` and `net472`, so it works in projects for .NET 8 or later and
.NET Framework 4.7.2 or later. Its only dependency is LibGit2Sharp, which brings the native libgit2 binaries for
Windows, macOS and Linux.

<Aside type="caution" title=".NET Framework apps">
  An SDK-style .NET Framework app gets the `win-x86` runtime identifier by default, and then fails to load libgit2
  (`BadImageFormatException` from `LibGit2Sharp.Core.NativeMethods`). Build it for 64-bit Windows instead:

  ```xml title="MyApp.csproj"
  <PropertyGroup Condition="'$(TargetFramework)' == 'net472'">
    <RuntimeIdentifier>win-x64</RuntimeIdentifier>
  </PropertyGroup>
  ```

  Apps for .NET 8 and later need nothing of the kind.
</Aside>

### From nuget.org

Releases are published to [nuget.org](https://www.nuget.org/packages/GitSnapshotter), so no setup is needed:

<Tabs syncKey="package-manager">
  <TabItem label=".NET CLI">
    ```sh
    dotnet add package GitSnapshotter
    ```
  </TabItem>
  <TabItem label="PackageReference">
    ```xml title="MyProject.csproj"
    <ItemGroup>
      <PackageReference Include="GitSnapshotter" Version="<version>" />
    </ItemGroup>
    ```

    Put the version you want in place of `<version>`. The latest is
    ![the latest version on nuget.org](https://img.shields.io/nuget/v/GitSnapshotter) (see
    [nuget.org](https://www.nuget.org/packages/GitSnapshotter)).
  </TabItem>
  <TabItem label="Central versions">
    With `Directory.Packages.props`, put the version there and leave it out of the project:

    ```xml title="Directory.Packages.props"
    <ItemGroup>
      <PackageVersion Include="GitSnapshotter" Version="<version>" />
    </ItemGroup>
    ```

    ```xml title="MyProject.csproj"
    <ItemGroup>
      <PackageReference Include="GitSnapshotter" />
    </ItemGroup>
    ```
  </TabItem>
  <TabItem label="PM Console">
    ```powershell
    Install-Package GitSnapshotter
    ```
  </TabItem>
</Tabs>

Release candidates (versions like `0.4.0-rc.1`) are published to nuget.org too. The commands above pick the latest
stable version; for the latest release candidate, add `--prerelease` (`-IncludePrerelease` in the PM Console), or
put its version in the project file. Every release is also on the
[GitHub releases page](https://github.com/BusHero/GitSnapshotter/releases), with its `.nupkg` attached and its
changes listed.

### Release candidates from trunk

Every build of `trunk` is a release candidate: the very packages a release would publish to nuget.org, at the version
it would be released as, with the build's run number after a `+`. `0.4.1+57` is run 57, a candidate for 0.4.1. To
try one before it is released:

<Steps>

1. Pick a run of the [Build and release workflow on `trunk`](https://github.com/BusHero/GitSnapshotter/actions/workflows/build.yml?query=branch%3Atrunk)
   whose jobs all passed; its summary names the candidate. Download its `release-candidate` artifact (you need to be
   signed in to GitHub), and unzip it into a directory next to your solution. Or, with the GitHub CLI:

   ```sh
   gh run download <run-id> --repo BusHero/GitSnapshotter --name release-candidate --dir gitsnapshotter-candidate
   ```

2. Add a `nuget.config` next to your solution that adds the directory as a package source. nuget.org stays
   available alongside it for your other packages:
   ```xml title="nuget.config"
   <?xml version="1.0" encoding="utf-8"?>
   <configuration>
     <packageSources>
       <add key="gitsnapshotter-candidate" value="gitsnapshotter-candidate" />
     </packageSources>
   </configuration>
   ```

3. Add the candidate's version, without the `+` and the run number:

   ```sh
   dotnet add package GitSnapshotter --version 0.4.1
   ```

   To go back to releases, set the version in your project file to one from nuget.org, and remove the source.

</Steps>

<Aside type="caution" title="NuGet caches by version">
  NuGet ignores what follows the `+`, so to NuGet every candidate for 0.4.1, and the 0.4.1 release itself, are the
  same package. Once one is in your global packages folder (`~/.nuget/packages`), restores keep using it. Before you
  switch to another candidate, or to the release of the same version, clear it:
  `dotnet nuget locals global-packages --clear`.
</Aside>

<Aside type="note" title="Package source mapping">
  If your `nuget.config` uses `<packageSourceMapping>`, add a `<package pattern="GitSnapshotter" />` entry under
  `gitsnapshotter-candidate`.
</Aside>

## The command-line tool

The tool is the `GitSnapshotter.Tool` [.NET tool](https://learn.microsoft.com/dotnet/core/tools/global-tools), and
installs the `gitsnapshotter` command. From 0.4.0 it needs the [.NET 8 runtime](https://dotnet.microsoft.com/download)
or later; 0.3.0 and earlier need the .NET 11 runtime or later. The latest stable version is
![the latest version on nuget.org](https://img.shields.io/nuget/v/GitSnapshotter.Tool), and the latest release
candidate ![the latest version on nuget.org, release candidates included](https://img.shields.io/nuget/vpre/GitSnapshotter.Tool).

### From nuget.org

Releases are published to [nuget.org](https://www.nuget.org/packages/GitSnapshotter.Tool), so no feed setup is
needed. These commands install the latest stable version; add `--prerelease` for the latest release candidate:

<Tabs syncKey="tool-scope">
  <TabItem label="Global">
    ```sh
    dotnet tool install --global GitSnapshotter.Tool
    gitsnapshotter help
    ```

    The command goes in `~/.dotnet/tools` (`%USERPROFILE%\.dotnet\tools` on Windows), which the .NET SDK
    installer puts on your `PATH`. Update with `dotnet tool update --global GitSnapshotter.Tool`.
  </TabItem>
  <TabItem label="Local (per repository)">
    A local tool is pinned in `.config/dotnet-tools.json`, so everyone who clones the repository, and CI, gets the
    same version with `dotnet tool restore`:

    ```sh
    dotnet new tool-manifest   # once, if the repository has no manifest yet
    dotnet tool install GitSnapshotter.Tool
    dotnet tool run gitsnapshotter help   # or: dotnet gitsnapshotter help
    ```

    This pins the latest stable version. To pin a specific one, add `--version <version>`.
  </TabItem>
</Tabs>

Each [GitHub release](https://github.com/BusHero/GitSnapshotter/releases) also has the tool's `.nupkg`, and the
app itself as a zip (`GitSnapshotter.Console_<version>.zip`) that runs with `dotnet GitSnapshotter.Console.dll`.

### Release candidates of the tool from trunk

Every build of `trunk` is a release candidate of the tool too, in the same `release-candidate` artifact as the
library. Download it and add the `nuget.config` as in [Release candidates from trunk](#release-candidates-from-trunk)
(steps 1 and 2), and mind the [cache](#release-candidates-from-trunk): a candidate and its release are the same
version to NuGet. Run these from the directory with that `nuget.config` (or pass `--configfile <path>`), with the
candidate's version without the `+` and the run number:

<Tabs syncKey="tool-scope">
  <TabItem label="Global">
    ```sh
    dotnet tool install --global GitSnapshotter.Tool --version 0.4.1
    gitsnapshotter --version   # 0.4.1+57.<commit>: the candidate's run and commit
    ```

    The command goes in `~/.dotnet/tools` (`%USERPROFILE%\.dotnet\tools` on Windows), which the .NET SDK
    installer puts on your `PATH`. Move to another candidate with
    `dotnet tool update --global GitSnapshotter.Tool --version <version>`.
  </TabItem>
  <TabItem label="Local (per repository)">
    A local tool is pinned in `.config/dotnet-tools.json`, so everyone who clones the repository, and CI, gets the
    same version with `dotnet tool restore`:

    ```sh
    dotnet new tool-manifest   # once, if the repository has no manifest yet
    dotnet tool install GitSnapshotter.Tool --version 0.4.1
    dotnet tool run gitsnapshotter help   # or: dotnet gitsnapshotter help
    ```
  </TabItem>
  <TabItem label="Run from source">
    With the .NET 11 SDK installed:

    ```sh
    git clone https://github.com/BusHero/GitSnapshotter.git
    cd GitSnapshotter
    dotnet run --project Source/GitSnapshotter.Console -- help
    ```

    `./build.sh` (or `build.cmd` on Windows) also builds a release candidate into `./release`. Install it with the
    version from its file name, `GitSnapshotter.Tool.<version>.nupkg`:
    `dotnet tool install --global GitSnapshotter.Tool --version <version> --add-source ./release`.
  </TabItem>
</Tabs>

<Aside type="tip" title="In GitHub Actions">
  `actions/setup-dotnet` puts `~/.dotnet/tools` on the `PATH`, so a global tool runs as `gitsnapshotter`. To test
  against a release candidate, download it in a step before with `actions/download-artifact`, giving its
  `repository`, `run-id` and a `github-token` that can read this repository's actions.
</Aside>
